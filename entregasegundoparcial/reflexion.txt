Al revisar este segundo avance del proyecto HeartGuard, me doy cuenta de que mi aprendizaje ha trascendido la simple escritura de código para adentrarse en el núcleo de la arquitectura y el diseño de sistemas complejos. Este módulo no se trató solo de construir un backend, sino de diseñar la columna vertebral de una plataforma robusta, escalable y segura, pensada para un entorno institucional. La lección más importante ha sido la evolución del pensamiento: pasar de un modelo de base de datos simple y familiar a una arquitectura multi-tenant normalizada en 3FN me obligó a considerar problemas reales como la redundancia de datos, la integridad referencial y, sobre todo, la escalabilidad a futuro.

Una de las decisiones de diseño más impactantes fue la centralización de la lógica de negocio en la base de datos a través de Stored Procedures. Al principio, mi instinto era manejar toda la lógica en la capa de aplicación (Go o Python), pero comprendí que para operaciones complejas y consultas analíticas, delegar este trabajo al motor de la base de datos no solo optimiza el rendimiento, sino que también simplifica enormemente los microservicios, permitiéndoles enfocarse en su verdadera tarea: gestionar la comunicación y el flujo de datos. Esto, combinado con una arquitectura de persistencia especializada —usando PostgreSQL para datos transaccionales, Redis para la agilidad de las sesiones y caché, e InfluxDB para el volumen masivo de datos de series de tiempo de los dispositivos IoT—, me enseñó a aplicar el principio de "usar la herramienta correcta para el trabajo correcto", un concepto fundamental en la ingeniería de software moderna.

Además, este avance me permitió entender el valor de las arquitecturas duales. Mientras que el sistema principal se basa en microservicios desacoplados que se comunican vía API, el diseño también contempla un backend de mantenimiento fuertemente acoplado. Este componente, de uso exclusivo para el superadministrador, opera directamente sobre la base de datos y se encuentra en un entorno completamente aislado, sin endpoints externos. Comprendí que este "acoplamiento fuerte" no es una debilidad, sino una decisión de diseño deliberada para maximizar la seguridad y el control en tareas críticas de mantenimiento, creando una clara separación entre las operaciones del día a día y la administración de la infraestructura.

Finalmente, este avance consolidó mi comprensión de la seguridad y la infraestructura en la nube. Diseñar una arquitectura con subredes públicas y privadas, donde un API Gateway actúa como único punto de entrada y los componentes críticos están aislados, dejó de ser un diagrama teórico para convertirse en una necesidad práctica de seguridad. Implementar un control de acceso basado en roles (RBAC) fue un reto que me enseñó la importancia de la granularidad en los permisos y la necesidad de un sistema de auditoría para la trazabilidad. En definitiva, este avance me ha permitido conectar la teoría de la integración de aplicaciones con la práctica real, demostrando que construir un sistema no solo es programar funcionalidades, sino diseñar un ecosistema coherente, seguro y preparado para el crecimiento.
